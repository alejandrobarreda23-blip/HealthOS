# PROSPECTIVE VALIDATION V1

## Aim

Validate whether repeated-event response summaries are stable and useful prospectively.

## Phase A — retrospective lock

Before seeing engine output:
- choose 10–20 known perturbation episodes;
- define expected observable pattern only where memory/context is reliable;
- freeze algorithm version.

## Phase B — silent prospective run

8–12 weeks:
- detect eligible perturbations automatically;
- calculate recovery;
- do not change user behaviour based on the model;
- record outputs.

## Phase C — evaluation

Assess:
- eligibility precision;
- missingness handling;
- false clean-event classification;
- recovery-time stability;
- sensitivity to provider switch;
- repeated-event consistency;
- whether same-session comparison materially changes when context filters are applied.

## Phase D — UI eligibility

Only expose longitudinal comparison when:
- technical verification passed;
- real-data execution passed;
- retrospective support exists;
- at least exploratory personal evidence is present.

## Never validate using headline agreement alone

Disagreement must be classified:
- implementation defect;
- missing data;
- incompatible context;
- genuinely uncertain physiology;
- incorrect prior expectation.
